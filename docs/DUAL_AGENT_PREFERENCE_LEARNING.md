# 双 Answer Agent 与用户偏好持续学习

## 生成与安全链路

同一次请求只执行一次混合检索和证据核验，然后把完全相同、顺序一致的已核验证据分别交给：

- `answer_generator_concise`：精炼证据版，优先给出核心结论和最相关引用。
- `answer_generator_detailed`：详细指导版，展开更多证据、适用边界和下一步建议。

两个候选都经过独立的输出安全 Agent 审核。只有两个版本均通过引用一致性和医疗安全
审核时，前端才显示二选一卡片；证据不足、高风险或审核失败时仍按原安全流程拒答、
重写或转人工，不会为了展示两个版本而放宽规则。

后端会为本次共同依据生成 `evidence_basis_id`，并强制比较两个版本使用的引用 ID。
两组引用只要有一项或顺序不一致，就中止双版本输出。因此两个版本只能在措辞、篇幅、
组织结构和解释深度上不同，医学依据不能不同。

## 用户选择与持续适配

用户点击“选择这个版本”后，`POST /api/feedback/preference` 保存成对偏好：被选择版本、
未选择版本、两种风格和请求上下文。重复选择是幂等的；改选会撤销旧票再记录新票。

系统为每个租户内用户维护独立画像：精炼版票数、详细版票数、偏好强度和画像版本。
下一轮回答开始前会读取画像，把更符合偏好的候选排在第一，同时仍保留另一版本供选择。
用户改选后，聊天历史也切换为所选答案，因此后续会话窗口与偏好画像保持一致。

这属于在线偏好适配，不会在生产请求中直接修改基础模型权重。直接在线微调医疗模型会带来
安全回归和灾难性遗忘风险；如需微调，应将脱敏偏好数据导出，在离线评测、安全审核和版本
回滚机制下训练新模型，再通过固定测试集比较后发布。

## 数据结构

- `chat_message.answer_variants_json`：保存两个安全候选。
- `answer_preference`：保存每条消息的用户成对选择。
- `user_answer_preference_profile`：保存持续更新的用户风格画像。
- Alembic `0007_pairwise_answer_preferences`：MySQL 表和消息字段迁移。
